# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mercora AI — a two-agent AI commerce platform (FastAPI + MongoDB backend, React/Vite frontend) built for the Razorpay AI Builder Buildathon (Track 01: AI Growth & Agentic Commerce). A **Customer Shopping Agent** handles NL search/recommendations/checkout; a **Merchant Growth Agent** mines order history for bundle/upsell opportunities that a merchant must explicitly approve. See `README.md` for the full architecture diagram, API surface, and demo flow — read it before making structural changes.

## Commands

Backend (from `backend/`, with `venv` activated):
```bash
source venv/Scripts/activate                     # Git Bash; PowerShell: .\venv\Scripts\Activate.ps1
pip install -r requirements.txt
python scripts/fix_dataset.py [--check]           # clean mercora_ml_dataset.csv in place (taxonomy, names, countries); idempotent
python scripts/fetch_product_images.py            # rebuild data/product_images.json from Wikimedia Commons (network; ~20 min)
python scripts/seed_kaggle_retail.py [mercora_ml_dataset.csv]  # load the catalog + order history (idempotent upsert; prunes stale retail_* docs)
python scripts/remove_synthetic_catalog.py [--apply]  # one-off: delete the old synthetic electronics data (dry run by default)
uvicorn app.main:app --reload --port 8000
python -m pytest tests/ -v                         # all tests
python -m pytest tests/test_ml.py -v                # single file
python -m pytest tests/test_ml.py::test_name -v     # single test
python scripts/evaluate_ml.py [--no-save]           # last-order holdout: P@K/R@K/Hit Rate/coverage (content vs rules vs popularity), rule holdout confidence, silhouette; saves to ml_evaluations for the merchant ML Evaluation page
```

The pytest suite is pure-function: it needs neither MongoDB nor the dataset CSV (`test_retail_dataset.py` builds synthetic CSV rows and loads the seed script via `importlib`). `evaluate_ml.py` and the seed script do need a reachable Mongo.

Frontend (from `frontend/`):
```bash
npm install
npm run dev       # http://localhost:5173, proxies /api -> http://localhost:8000 (see vite.config.ts)
npm run build     # runs `tsc -b` then vite build — treat TS errors as build failures
npm run lint      # oxlint
```

MongoDB: local instance or `docker run -d --name mercora-mongo -p 27017:27017 mongo:7`. Connection string comes from `.env` (`MONGODB_URI`, `DATABASE_NAME`) at the repo root, read by `backend/app/config.py`.

There is no backend lint script configured; rely on `tsc -b`/`oxlint` (frontend) and pytest (backend) as the correctness gates.

## Architecture

**Data flow is the point of this app**: customer purchases → order history in MongoDB → ML mining (association rules + segmentation) → scored growth opportunities → merchant approval → written back as `bundles` → immediately surfaced by the Shopping Agent's cross-sell as real offers. Any change to one stage should be checked against this loop, not treated in isolation.

**Backend layout** (`backend/app/`):
- `agents/` — `shopping_agent.py` and `growth_agent.py` each expose an explicit tool registry (e.g. `search_catalog`, `get_recommendations`, `add_to_cart`) — agents never execute arbitrary code, only these named tools. `llm_provider.py` defines the `LLMProvider` ABC with `AnthropicProvider`, `GeminiProvider` (Google Gemini, needs `LLM_API_KEY` + `GEMINI_MODEL`), `OpenAIProvider` (needs `LLM_API_KEY` + `OPENAI_MODEL`), `OllamaProvider` (local model via `ollama serve`, no API key — `OLLAMA_BASE_URL`/`OLLAMA_MODEL` in `.env`), and a deterministic regex/keyword `FallbackProvider`; `get_llm_provider()` picks based on `LLM_PROVIDER`/`LLM_API_KEY`. `parse_shopping_intent_llm()` calls the live provider for structured intent JSON and falls back to the deterministic `parse_shopping_intent()` on any failure (timeout, malformed JSON, unconfigured provider). Every provider returned by `get_llm_provider()` is wrapped in `_InstrumentedProvider`, which logs failures and persists estimated token counts to `llm_usage_events` (surfaced by `GET /api/llm-usage`) — add new providers inside that wrapper, not around it. **The fallback path must always work with zero API keys** — never add a code path that requires an LLM key to function.
- `search_catalog()` in `shopping_agent.py` treats `category` as a *preference* (OR), not a strict filter, matched together with keyword regexes against product `name`/`tags` — companion/bundle products are deliberately tagged with their parent category for association mining even when a keyword (e.g. "mouse") describes them more precisely, so a strict category-AND-keyword filter silently excludes real matches. If search results look wrong, check this OR-matching logic before assuming the LLM/NLU layer is at fault.
- `ml/` — `recommendation.py` (TF-IDF + cosine similarity blended with popularity), `association.py` (mlxtend Apriori over order line-items), `segmentation.py` (KMeans over log-scaled RFM features, recency measured from the latest order; duplicate segment labels are qualified by whichever of recency/spend separates them), `opportunity.py` (scores opportunities as `0.35·affinity + 0.25·conversion + 0.20·revenue + 0.20·confidence`; no upsells from `Uncategorized`), `explain.py` (the `explanation` attached to every recommendation: `method` co_purchase/content/intent/popularity, a `summary`, display `signals` and raw `metrics`; content and intent explanations name the TF-IDF terms whose per-term products sum to the cosine similarity; co-purchase confidence is oriented to the viewed product using the rule's stored `support_a`/`support_b`, and a rule missing a field omits that signal rather than estimating it), `evaluation.py` (`run_evaluation()`, shared by `scripts/evaluate_ml.py` and `POST /api/merchant/ml-evaluation/run`; it calls `similar_products(..., explained=False)` because explaining hundreds of candidates per customer made a run ~3.5× slower). All computed from real seeded Mongo data — no fabricated/hardcoded numbers. When no rule involves a product, `get_cross_sell_products` falls back to content similarity with `method: "content"`; callers must not present those as co-purchases (the product page's "Frequently bought together" and the agent's "customers frequently add" line both check the method).
- Order data access (`agents/growth_agent.py`): revenue, product sales, category revenue and per-customer RFM are MongoDB aggregations over **all** paid orders (`fetch_order_totals`, `fetch_product_sales`, `fetch_customer_rfm`). Only association mining loads baskets — the `MINING_ORDER_LIMIT` most recent paid orders, product ids only. Don't reintroduce "fetch every order document": it took 12–17s from Atlas and silently truncated totals at the old 10k cap.
- `services/guardrails.py` — the sole authority clamping AI-proposed discounts (`clamp_discount`, `validate_bundle_discount`); the growth agent can only *propose*, this is what actually enforces limits. Any endpoint that applies an AI-suggested discount must go through here.
- `services/razorpay_service.py` — orders/signature verification are server-side only; when `RAZORPAY_KEY_ID`/`SECRET` are blank, falls back to a deterministic mock order + mock signature so checkout is always demoable without real credentials.
- `services/audit.py` — every agent action (proposal, approval, guardrail clamp, bundle creation) must call `log_action(...)` to the `audit_logs` collection.
- `services/events.py` — `track(event_type, customer_id, data)` records customer funnel events (search, recommendation shown/clicked, upsell, cart, payment) into `search_events`/`recommendation_events`/`cart_events` per the `EVENT_COLLECTIONS` map; these feed the conversion signals used by the growth side. New event types need an entry in that map or they land in `search_events`.
- `api/auth.py` — OTP phone auth (`/signup/request-otp`, `/signup/verify-otp`, `/login/request-otp`, `/login/verify-otp`). No SMS provider is wired, so the OTP is mocked: logged and echoed in the response with `mock: true` (same zero-credential pattern as payments). OTPs live in `otp_verifications` with a TTL index, so `expires_at` must stay a BSON datetime, not an ISO string.
- `main.py` — the lifespan logs whether a live LLM provider is active and, if Mongo is unreachable at startup, keeps serving (DB-dependent routes return 503) rather than crashing.
- `api/` — one router per resource; `opportunities.py`'s approve endpoint is the one place growth-agent output is written back to the catalog, and it must always re-validate through `guardrails.py` regardless of what the agent proposed.
- `database/connection.py` — `get_db()`/`ensure_indexes()`; add new indexes here rather than ad hoc in queries. Whole-catalog loads use `CATALOG_FETCH_LIMIT`; `RecommendationEngine.similar_products` computes one similarity row per call — don't reintroduce a precomputed N×N matrix (~150MB at the retail catalog's size).

**Frontend layout** (`frontend/src/`): pages under `pages/` (customer: `Landing`, `Auth` at `/login`, `Shop`, `ProductDetail`, `Cart`, `Checkout`, `Orders`, `Invoice`) and `pages/merchant/` (`Overview`, `Analytics`, `Products`, `Opportunities`, `MlEvaluation`, `Copilot`, `Audit`, `Settings`, nested under `MerchantLayout`; `MlEvaluation` reads the latest `ml_evaluations` report, and its chart colours are categorical slots 1–3 of the dataviz reference palette, fixed per method), routed in `App.tsx`. Customer routes other than `/` and `/login` are wrapped in `RequireAuth`; merchant routes are not gated. `lib/api.ts` holds the axios instance plus client-side identity: after OTP verification `setAuthenticatedCustomer()` stores the customer id/name and an `mercora_authenticated` flag in localStorage (`isAuthenticated()`, `getCustomerId()`, `logout()`), and `getSessionId(key)`/`resetSessionId(key)` keep per-tab chat sessions in sessionStorage. No JWT is issued or sent; the backend trusts the `customer_id` the client passes. Every product image goes through `components/ProductImage.tsx`: an empty or failing `image` renders a generated tile (no network request) whose colour/icon are derived from the category/subcategory *text*. Nothing in the frontend may hardcode category names — the taxonomy lives in Mongo, and the Shop filters come from `GET /api/products/categories`. `ProductDetail` shows `image_credit` attribution under the photo. `components/WhyThis.tsx` renders a product's `explanation` (in `ProductCard` and the assistant's product rows). Data fetching goes through TanStack Query hooks (see `hooks/useCart.ts` as the pattern). **Homepage** (`pages/Landing.tsx`, lazy-loaded): opens with `components/store/intro/` (SVG truck + package, Canvas particle burst, one GSAP master timeline; all timings in `introConfig.ts`; plays once per session via sessionStorage, skippable, reduced motion shows the brand frame), then a scroll story in `components/store/story/`. The explosion's fragments (60 box-edge lines, 120 dots, 18 shapes, all drawn by one fixed Canvas 2D layer, `FragmentField.tsx`) persist for the whole page and move between per-fragment target formations in `fragments.ts` (scattered → box → moved box → structure → world → three range outlines → frame → ring round the AI search → rebuilt box → opened). The renderer eases toward one number, `story.target` in `storyState.ts`, which only the "director" in `Landing.tsx` writes, deriving it from scroll position and registered scene ranges. Don't write it from individual timelines: whichever inactive timeline renders last on a ScrollTrigger refresh wins. The outlines are abstract shapes for a range, and the product shown beside each is a real top seller from that range. `placeLines` must stay total-preserving for outlines with more segments than line fragments; a non-terminating version once froze the page at the teapot. There is no three.js. Tailwind v4 is wired via the `@tailwindcss/vite` plugin and `@import "tailwindcss";` in `index.css` — not the old PostCSS setup.

**Seed data** (`backend/scripts/seed_kaggle_retail.py`): the store's catalog and order history are exactly `mercora_ml_dataset.csv` (repo root, gitignored at 108MB; cleaned Kaggle Online Retail invoices with category/subcategory, implicit rating, popularity and RFM columns). The file's values are maintained by `scripts/fix_dataset.py`: every product's category/subcategory (10 categories / 57 subcategories) comes from the ordered product-*type* regex rules in `TAXONOMY_RULES` — priority types first, then cards/gift wrap, then Christmas/Easter themes, then the rest. The file's original labels were a first-keyword match (19% blank, many wrong); an ML name classifier was tried and does not transfer to the unlabeled products, so fix misfiles by editing/reordering rules and re-running, and review the per-subcategory output (a rule that matches nothing exits non-zero). The original file is backed up as `mercora_ml_dataset.original.csv` (gitignored). `Uncategorized` (`UNCATEGORIZED` in `app/schemas/product.py`) remains only as the seed's fallback for blank rows. Prices go GBP→INR at ×105, guest invoices are skipped, missing ratings get the category median (`rating_imputed: True`). Photos come from `backend/data/product_images.json` (committed; built by `fetch_product_images.py`): openly licensed Wikimedia Commons photos of each product's *type* — illustrative, not the exact item — hotlinked from `upload.wikimedia.org`, with author/licence/source in `image_credit`. Order dates are shifted by one fixed `DATE_SHIFT` so the file's last invoice (2011-12-09) lands on 2026-10-23 — intervals are exact and the original is in `source_order_date`; keep the shift constant so re-imports stay idempotent. Ids are `prod_retail_<stock code>` (the CSV's `OR-` prefix stripped, so ids match the earlier import from the raw `Online_Retail.csv`, which is still committed at the repo root but no longer read by anything), `cust_retail_<id>`, `order_retail_<invoice>`. The old synthetic electronics seed (`seed_data.py`) and the loremflickr image script were deleted — loremflickr returns HTTP 500 for every URL. The keyword→category hints in `llm_provider.CATEGORY_KEYWORDS` were derived from the cleaned file (only words naming ≥5 products that are ≥85% pure for one category; "christmas" is a documented exception) and match on word boundaries — re-derive them if the taxonomy rules change.

## Environment

`.env` at repo root (see `.env.example`): `MONGODB_URI`, `DATABASE_NAME`, `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` (blank = mock payment mode), `LLM_API_KEY`/`LLM_PROVIDER` (blank/`none` = deterministic fallback NLU), `JWT_SECRET`/`JWT_ALGORITHM` (loaded in `config.py` but not currently used by any route), `FRONTEND_URL`, `BACKEND_URL`. Never commit real secrets into `.env` — it's gitignored, but double-check before any commit that touches it.

## Deployment

Detailed in `DEPLOYMENT.md`. The live setup is a **single Vercel project using Vercel Services**: the root `vercel.json` defines a `frontend` service (Vite static build) and a `backend` service (`backend/app/main.py` run as a Python function), routes `/api/*` to the backend and everything else to the frontend; `frontend/vercel.json` only adds the SPA fallback rewrite. The database is MongoDB Atlas. A split deployment (backend on Railway/Render via `backend/Dockerfile`, which reads `$PORT`, with `VITE_API_BASE_URL` set at frontend build time) still works but isn't the live setup.

**Never deploy with `LLM_PROVIDER=ollama`.** On Vercel it already caused production 500s (`FUNCTION_INVOCATION_FAILED`): calls to `localhost:11434` hang until the platform kills the function, before the code's try/except fallback can run. Hosted deployments need `gemini`, `openai`, or `anthropic` with a real `LLM_API_KEY`, or `none` for the deterministic parser. Hosted provider calls are capped by `HOSTED_API_TIMEOUT` (10s) in `llm_provider.py`, and the growth agent fetches orders/products only once per request. Keep both in place, because function time limits are the real constraint here.

## Windows-specific notes

- `pandas`/`numpy`/`scikit-learn` versions in `requirements.txt` are pinned to ones with prebuilt Windows wheels for Python 3.13 (avoids a Meson/Visual Studio build-from-source requirement) — don't casually bump them without checking wheel availability.
- `setuptools<81` is pinned because the razorpay SDK imports `pkg_resources`, which newer setuptools removed.
- Use `np.ptp(arr)`, not `arr.ptp()` — removed in NumPy 2.0.
